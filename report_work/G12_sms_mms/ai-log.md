# AI 协作纪实

> 记录本次分析中 AI 参与的部分、被推翻的判断、以及人工核验的方式。
> 原则：AI 可以提速，但**每条结论必须回到源码**；这里只记录真实发生过的事，不美化。

## 0. 分工

| 环节 | AI 承担 | 人工核验 |
|---|---|---|
| 目录勘察 | 遍历、识别工具用途、读四个脚本 | 抽查脚本参数与退出码 |
| 链路追踪 | `oh_trace.py` 找符号 + 逐文件读实现 | 对每个锚点看一遍上下文 |
| 锚点取数 | 批量定位行号 | 用 `oh_verify.py` 全量复跑 |
| 报告成稿 | 结构化、写作、图表 | 事实与措辞复核 |
| 版本口径 | 比对两个 commit | 用 `git describe` 独立确认 |

## 1. AI 说对了什么（可复核的部分）

- 链路形状：应用 → Proxy → Stub → Service → InterfaceManager → SendManager → GSM/CDMA Sender → RIL/IMS。8 跳的每一跳都能在源码里指到具体函数，已全部挂锚点。
- 分片顺序：**先编码再按字节切**，不是先按字符切。这一条通过 `SplitMessage` 中"先 `DecodeMessage` 拿 `encodeLen`、后 `GetSegmentSize` 算段长"的调用顺序确认。
- 多段聚合点：`unSentCellCount` 归零才回调，`hasCellFailed` 决定最终成败。这是全链路最容易被讲错的地方。

## 2. AI 说错了什么（三处，均已改正）

### 2.1 第一处：把"版本领先"直接当成"锚点必然失效"

**AI 的原话**：本地仓在 master，比 7.0-Release 多 46 个提交，"从本地取的行号在教师侧一定校验失败，必须先重拉基线"。

**怎么被推翻的**：导出 `origin/OpenHarmony-7.0-Release` 全量副本后，对同一批函数在两个树上逐条取行号：

```bash
grep -n "int32_t SmsService::SendMessage" services/sms/sms_service.cpp   # 146 / 146
grep -n "void SmsSender::HandleMessageResponse" services/sms/sms_sender.cpp   # 96 / 96
grep -n "void SmsInterfaceStub::OnSendSmsTextRequest" services/sms/sms_interface_stub.cpp   # 161 / 161
```

三个文件、三个函数，行号完全一致。再核对 `git diff --stat`：41 个文件有改动、+1291/−29；其中还包含**语义改动**——`sms_interface_stub.cpp` 第 33、113 行的卡槽上限由 `SIM_SLOT_COUNT` 换成 `SIM_SLOT_COUNT_MD`，就落在锚点（161 行）上方。但两处都是等行替换、没有增删行，所以行号未动。

**真相**：**版本号领先 ≠ 行号漂移**。漂移只会发生在"锚点所在的函数上方有增删行"的文件里。

**留下的方法**：不靠版本号猜，靠"双树批量比对"验。本报告最终 86 个锚点在两个版本上均 0 FAIL（见 `repo` 目录的校验输出），这是实测结论而非推断。

### 2.2 第二处：把权限校验放在了 Stub 层

**AI 的原话**：`OnSendSmsTextRequest` 是 IPC 入口，"权限校验理应在这里"。

**怎么被推翻的**：对 `services/sms/sms_interface_stub.cpp` 全文检索 `Permission`，命中数为 **0**。真正的收口在服务层：

```bash
grep -n "CheckSmsPermission" services/sms/sms_service.cpp   # 155、308、337
```

Stub 只做两件事：卡槽号边界检查、地址去空格。

**真相**：权限与业务策略都在 `SmsService::SendMessage` 里，Stub 是纯协议层。

**影响**：这条纠错直接改写了报告的"弊端"一节——原本打算写"Stub 与 Service 重复校验"，实际是"校验只在 Service 一层，任何绕过 Service 复用 Stub 的新代码都会绕开权限"。

### 2.3 第三处：把"剩余计数"说成了共享指针

**AI 的原话**：多段聚合时"创建一份共享的剩余计数和一个共享的失败标志，每个分段都持有同一份指针"。

**怎么被推翻的**：`GsmSmsSender::TextBasedSmsSplitDelivery` 里，两个东西的传递方式并不一样——

```cpp
indexer->SetUnSentCellCount(*unSentCellCount);   // 解引用后按值传，形参是 const uint8_t
indexer->SetHasCellFailed(hasCellFailed);        // 传 shared_ptr<bool>，真共享
```

**真相**：失败标志是共享的，剩余计数是**每段一份副本**；同步靠 `UpdateUnSentCellCount` 的广播递减——遍历缓存表，把所有同 `msgRef` 的分段一起减 1。共享的不是变量，是节奏。

**顺带的连带纠错**（同一次复核推翻的另外两处）：

1. "18 个汉字会被切成 2 段"：18 个汉字在 UCS2 下只有 36 字节，远不到单条上限 140，**一条就发完**。改用 100 个汉字（200 字节 → 134+66，即 67+33 个汉字）才成立。
2. "两层回执都会改库、发广播"：`StatusReportAnalysis` 函数体内只有回 ACK 与 `OnSmsDeliveryResult`，**没有写库动作**——那行"save the message to db"只是注释。

**教训**：AI 最容易在"两个东西看起来一起传进去"的地方出错，实际一个是引用、一个是拷贝。这种差别只能逐行看形参，不能凭语义直觉补。

## 3. AI 没能做的事（明确边界）

- 没上机，没有真实日志。因此报告只主张 L1，不冒充 L2。
- 没有反编译或阅读 RIL 侧实现，`CoreManagerInner::SendGsmSms` 之后的空口行为不在本报告范围内。
- 没有验证 `MAX_GSM_7BIT_DATA_LEN` / `MAX_UCS2_DATA_LEN` 的具体取值——它们不在本切片内定义，报告只用仓内可证的 153 / 134。
- 彩信与 CDMA 分支只到分流点，未展开。

## 4. 可复现的核查步骤

1. `git -C telephony_sms_mms rev-parse HEAD`，确认与报告头部记录的 commit 一致。
2. 按报告 5.2 的命令跑 `oh_verify.py`，应看到 0 FAIL。
3. 任取 3 个锚点，用 `oh_trace.py` 独立复现行号，与报告一致。
4. 对本纪实第 2 节的两条 `grep` 命令直接执行，应得到文中给出的行号。

## 5. 一个更隐蔽的失败：内行看得懂，外行看不懂

**现象**：第 3 页第三张图原本画的是 8 个核心类的依赖关系（`classDiagram`）。对读完这个仓的人，那是信息密度最高的一张；但对着屏幕问"这个仓是干什么的"，它一句也答不上来。收到的反馈原话是："没用过鸿蒙的人完全不知道你在说什么。"

**原因**：AI 的默认读者是"能读懂类图的人"。它把**准确**当成了**清楚**——类图确实准确，但准确只对已经知道答案的人有效。更糟的是，封面只写了题目（"一条短信的发送"），全篇没有一处交代"讲的是什么东西"，于是每一页都在给一个陌生人讲家谱。

**修法（两处，都不增删事实）**：

1. 封面加一句定义，句子结构照搬仓库自带代码地图的"部件定位"：**它是什么（独立部件）→ 边界在哪（从对外的 TypeScript API 声明，到与 Modem 交互）**。这句能回收给后面每一页：讲层=它落在第几层，讲链=这句话怎么走，讲目录=这句话的代码在哪。
2. 第 2 页把"四个术语"换成一张六行定位表（部件 / 系统服务 / 启动配置 / 职责 / 上游 / 下游），第三列专门写给没接触过鸿蒙的人。类图没删，降级到报告 1.5.1 与备用页速答。

**教训**：**判断一段话清不清楚，不能问写它的人。** AI 尤其不能自查这一点——它知道全部上下文，所以任何省略都"显然"。这一条必须靠外部读者反馈，而且越早越好：这次是在七轮核验、所有事实都对之后才暴露的，说明**事实正确与表达有效是两件独立的事**，前者可以靠锚点校验，后者不能。

**顺带一个可复用的判据**：如果一句话需要读者先知道三个名词才能听懂，那它就不是"定义"，是"补充"。定义必须能在一个陌生读者的零上下文里成立——本项目的那句是："它是一个独立部件，把短信彩信从对外接口声明，实现到和基带打交道。"
